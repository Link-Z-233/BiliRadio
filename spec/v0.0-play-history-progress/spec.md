# Feature Specification: 播放历史与进度记录（B 站历史同步预留）

**Created**: 2026-10-06  
**Status**: Draft  
**Input**: User description: "我想做播放历史和进度记录，来个未来的与b站的历史记录同步做准备"（目标文档 PROJECT_NOTES.md 第三章「播放历史云端同步」条目；B 站历史数据模型参照 PiliPlus 实现）

## Overview

将本地播放历史从「只记看过什么」升级为「记看到哪里」：每条历史记录补齐 B 站历史模型的关键字段（cid、progress 秒、duration、view_at），播放期间持续更新进度；切回或重播同一内容时智能续播（未听完续播、已听完从头）。历史面板同步增强：显示进度、续播标识、支持单条左滑删除（补 PROJECT_NOTES.md KI-3 播放历史项）。数据层与字段单位对齐 B 站历史接口格式，为未来登录态下的云端同步（心跳上报/历史拉取合并）预留映射边界，但本轮不发起任何云端请求。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每集独立进度与智能续播 (Priority: P1)

我在听一集 40 分钟的视频，听了 12 分钟切去别的内容（或退出 App）。之后从历史、队列或订阅源再次播放这一集时，App 从 12 分钟附近继续，而不是从头开始；如果这集我已经基本听完（接近结尾或自然播完），再次播放则从 00:00 开始。

**Why this priority**: 「记住听到哪」是播客类应用的核心体验，也是本次需求「进度记录」的主体；现有的断点记忆只覆盖最后一次退出时的那一集，无法支撑多集来回切换和历史回跳。

**Independent Test**: 播放 A 内容超过 30 秒后切到 B，再切回 A（经历史面板或队列），验证 A 从上次进度续播；单独把 A 拖到接近结尾听完后再播，验证从 00:00 开始。

**Acceptance Scenarios**:

1. **Given** A 内容已播放 12 分钟且未达完播阈值，**When** 用户切到 B 再切回 A，**Then** A 从上次进度附近（误差不超过一个进度记录周期）续播。
2. **Given** A 内容已自然播放至结尾（或进度 ≥ 完播阈值），**When** 用户再次播放 A，**Then** A 从 00:00 开始播放，且历史记录标记为已听完。
3. **Given** 应用正在播放 A 时被用户划掉/被系统杀死，**When** 重新打开并播放 A，**Then** 进度最多回退一个进度记录周期，不回到 00:00。

---

### User Story 2 - 历史数据模型对齐 B 站（同步预留） (Priority: P2)

App 的每条播放历史包含 B 站历史接口所需的核心字段：bvid、cid（分P）、progress（秒，-1 表示已看完）、duration（秒）、view_at（秒级时间戳）等；本地字段命名与单位转换集中在一处，未来接云端同步时可直接映射为上报/拉取格式。旧版本的历史数据升级后平滑保留，一条不丢。

**Why this priority**: 这是「为未来同步做准备」的直接落地——不把字段和单位理顺，后续云端同步（心跳 played_time、cursor 拉取 progress/view_at）每次都要做散装换算，极易出错。

**Independent Test**: 升级安装后打开历史面板，旧记录全部可见；查看存储数据，确认新字段（progress/duration/cid/view_at）存在且单位为秒；同一数据结构可直接映射到 B 站历史条目格式（人工核对字段对照表）。

**Acceptance Scenarios**:

1. **Given** 旧版本历史文件（无 progress/cid/duration 字段），**When** 新版本首次加载，**Then** 全部旧记录平滑迁移为含新字段的条目（progress 缺省、cid 未知占位），无记录丢失、无崩溃。
2. **Given** 播放了一段内容，**When** 查看该条历史记录，**Then** progress 与 duration 以秒为单位、view_at 为秒级时间戳，且与 B 站历史条目字段一一对应。
3. **Given** 本特性全部功能运行，**When** 监听网络请求，**Then** 不出现任何 B 站历史同步相关请求（同步仅预留、不实现）。

---

### User Story 3 - 历史面板增强：进度展示与单条删除 (Priority: P3)

我打开设置页的播放历史面板：每条记录能看到听到哪里（剩余时长或「已听完」标识）；点某条直接按智能续播规则播放；某条不想要了，左滑露出「删除」按钮，点击即删（对齐 KI-3 的交互约定，不做滑过阈值直删）。

**Why this priority**: 进度数据要看得见才有感知；单条删除是已登记的缺口（KI-3 播放历史项），顺手补齐，避免历史只能「一锅端」。

**Independent Test**: 打开历史面板查看进度信息与标识；左滑任意条目出现删除按钮，点击后该条消失且重启 App 后仍不出现；点击条目验证续播行为与 US1 一致。

**Acceptance Scenarios**:

1. **Given** 历史面板中存在未听完的条目，**When** 面板打开，**Then** 该条目显示剩余时长（或等价的进度信息）。
2. **Given** 历史面板中存在已听完的条目，**When** 面板打开，**Then** 该条目显示「已听完」标识，不显示剩余时长。
3. **Given** 历史面板中任意条目，**When** 用户左滑后点击「删除」，**Then** 该条从列表移除并持久化；重启 App 后仍不存在；其余条目不受影响。
4. **Given** 历史面板中某未听完条目，**When** 用户点击该条目，**Then** 按智能续播规则播放（续播）。

---

### Edge Cases

- **旧数据迁移**：旧 `PlayHistoryItem` 无 progress/duration/cid 字段——加载时平滑补默认值，不丢记录（US2 场景 1）。
- **duration 未知**：视频时长可能为 0/未知（BiliVideo.duration 缺失），此时无法计算完播比例——播放器拿到真实时长后回填；duration 未知时不做「已听完」判定，仅记录 progress。
- **同一内容重复播放**：同 bvid（同 cid）再次播放时更新同一条记录的 progress 与 view_at，并移到列表最前（沿用现去重置顶逻辑），不产生重复条目。
- **多分P（cid 变化）**：以 bvid 为历史条目主键、cid 为分P属性，进度记录跟随当前实际播放的 cid；BiliRadio 场景绝大多数为单 P，多 P 视频以最后播放的分P为准。
- **进度记录时机与崩溃容忍**：切歌、暂停、页面/应用退出时立即写盘；播放中按固定周期节拍写盘——异常退出最多丢一个节拍的进度。
- **清空历史**：现有「清空播放历史」行为保持，清空后进度记录一并清除。
- **全局断点与每集进度并存**：现有「上次退出断点续播」（KEY_LAST_INDEX/KEY_LAST_POS_MS）行为不变，每集进度是新增能力层；两者数据独立，互不干扰。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每个播放过的内容记录独立播放进度：条目以 bvid 标识、携带 cid（分P），progress 以**秒**为单位，并在播放期间持续更新。
- **FR-002**: 系统 MUST 记录条目的总时长 duration（秒）；时长在播放器获取到真实时长后回填更新。
- **FR-003**: 智能续播——再次播放某内容时，系统 MUST 按以下规则决定起点：上次进度 ≥ 完播阈值或已标记看完 → 从头播放；否则 → 从上次进度续播。完播阈值默认 95%。
- **FR-004**: 完播标记——自然播放至结尾或进度达到完播阈值时，系统 MUST 将该条目标记为已看完（对齐 B 站 progress=-1 语义）。
- **FR-005**: 每条历史条目 MUST 包含：bvid、cid、title、ownerName、cover、sourceType（沿用现字段）、progress（秒，-1=看完）、duration（秒）、view_at（秒级时间戳）。
- **FR-006**: 加载旧格式历史数据时，系统 MUST 平滑迁移：全部旧记录保留，缺失字段取默认值（progress=0、cid=0、duration=0），不崩溃、不丢数据。
- **FR-007**: 进度 MUST 在以下时机持久化：切换内容、暂停、应用/页面退出，以及播放中的周期性节拍（节拍间隔不大于 30 秒）；异常退出时进度回退不超过一个节拍。
- **FR-008**: 播放历史面板 MUST 为每条条目展示进度状态：未听完显示剩余时长或进度百分比，已听完显示「已听完」标识。
- **FR-009**: 播放历史面板条目 MUST 支持左滑露出「删除」按钮、点击执行单条删除（不做滑过阈值直删）；删除立即生效并持久化，且不影响其他条目。
- **FR-010**: 点击播放历史面板条目 MUST 按智能续播规则（FR-003）开始播放。
- **FR-011**: 本地历史条目与 B 站历史接口格式之间的字段映射与单位转换 MUST 集中在独立的数据层边界（模块/服务），供未来同步模块复用。
- **FR-012**: 本轮 MUST NOT 发起任何 B 站历史同步相关的网络请求（心跳上报、历史拉取、删除同步等均为未来范围）。
- **FR-013**: 历史容量沿用现有上限（200 条），溢出时裁剪最旧条目。
- **FR-014**: 现有「清空播放历史」功能行为保持，清空后条目与进度记录一并清除。

### Key Entities *(include if feature involves data)*

- **播放历史条目（PlayHistoryItem 升级）**: 一条内容的观看记录。属性：bvid（唯一标识）、cid（分P标识，同步关键字段）、title、ownerName、cover、sourceType（来源类别：收藏夹/合集/本地）、progress（秒，-1 表示已看完）、duration（秒）、view_at（秒级时间戳，最后播放时间）。同一 bvid 全局仅一条，重复播放时更新并置顶。
- **B 站历史条目映射（同步预留边界）**: 本地条目与 B 站历史接口条目（bvid/cid/progress/duration/view_at/title/show_title/author_name/cover 等）之间的字段对照与单位换算规则，作为未来云端同步模块的输入。本轮仅定义映射，不产生网络行为。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 重播任意未听完内容，100% 从上次进度续播，进度误差 ≤ 一个记录节拍（≤30 秒）。
- **SC-002**: 重播已看完内容，100% 从 00:00 开始。
- **SC-003**: 从旧版本升级后，历史记录丢失数为 0。
- **SC-004**: 历史面板每条条目可见进度信息；单条删除即点即生效，重启后仍保持删除状态。
- **SC-005**: 本特性全流程运行期间，B 站历史同步相关网络请求数为 0。

## Assumptions

- 完播阈值取 95%，作为常量定义，不暴露为用户设置（对齐 B 站「接近结尾视为看完」的隐式行为）。
- cid 取播放器解析流时拿到的当前分P cid；绝大多数场景为单 P。
- view_at 存储用秒级时间戳（对齐 B 站），界面展示格式沿用现有日期格式化。
- 进度写盘节拍间隔在 15–30 秒区间内由实现确定，需满足 FR-007 上限。
- 「同步预留」的范围 = 字段/单位对齐 + 集中映射边界；云端调用、心跳策略、冲突合并均不在本轮范围。
- 现有全局断点续播（KEY_LAST_INDEX/KEY_LAST_POS_MS）、队列快照行为保持不变。
- 历史存储沿用现有本地 JSON 文件方案（迁移与扩字段在该方案内完成），不引入新存储设施。
