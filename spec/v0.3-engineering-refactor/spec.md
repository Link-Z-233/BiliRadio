# Feature Specification: 工程重构总规划（Engineering Refactor）

**Created**: 2026-10-10
**Status**: Draft
**Input**: User description: "重构这个项目：界面风格统一、架构边界重构、KI-9 页界统一、状态管理 V2 渐进迁移；以 API 26 为既定基线（不考虑低版本兼容）。本次对话只做规划（产出 spec/plan/tasks），不实施代码改动。"

## Overview

本特性是 BiliRadio 的**工程重构总规划**，把一次大型现代化拆成多个可独立交付、独立验证、独立回滚的阶段。**API 26 为全局既定前提**：兼容基线升至 26.0.0 属前置落地项（不再作为独立用户故事），本次规划整体基于 API 26，**不考虑任何 API<26 兼容设计**。

- **Phase B · KI-9 页界统一**：修复订阅翻页时 APP 签名链（20 条/页）与 Web 退避链（30 条/页）页界不对齐导致的漏条目问题。
- **Phase C · 界面风格统一（设计令牌 + 组件规范）**：统一定义色彩/圆角/间距/字号令牌并全局替换散落硬编码，再归一列表行/卡片/弹窗/空态等重复部件的样式，消灭视觉碎片化。
- **Phase D · 架构边界重构（等级 1）**：保持现有单例 + V1 状态管理范式，理清模块边界、依赖方向与服务职责，**不改变任何功能行为**。
- **Phase E · V2 渐进迁移路线图（远期，仅规划）**：状态管理从 V1 渐进迁移到 V2，按「模型层 → 独立组件 → 页面 → 全局状态」分块推进，**本期不实施**。

**全局前提（Phase A · API 26 基线化）**：`compatibleSdkVersion` 升至 26.0.0、移除 `[API24-COMPAT]` 守卫、版本号 0.3.0/3000、活跃文档同步——作为后续所有阶段的前置条件落地，验收标准见 FR-A 系列。

规划交付物为 `spec/plan/tasks` 三份文档，作为后续分轮实施的权威依据。

## User Scenarios & Testing

### User Story 1 - 订阅翻页不漏条目（Phase B · KI-9）(Priority: P1)

用户向下滚动 UP 投稿订阅加载更早内容时，无论当前走 APP 签名链还是 Web 退避链，翻页页界都对齐，不会因两条链路页大小不同（20 vs 30 条/页）而在链路切换/降级后漏掉条目。（收藏夹/合集/系列为单链翻页，无双链页界问题。）

**Why this priority**: 漏条目直接影响订阅内容的完整性，是已登记的真实缺陷（KI-9），且改动相对可控。

**Independent Test**: 触发链路降级/回切场景，对比翻页结果无漏条、无重复。

**Acceptance Scenarios**:

1. **Given** 订阅源走 APP 签名链，**When** 触发降级切到 Web 退避链继续翻页，**Then** 前后条目连续，无遗漏无重复。
2. **Given** 任意订阅源，**When** 触底翻页直至到底，**Then** 全量条目完整，无整段缺失。
3. **Given** 翻页过程，**When** 发生链路切换，**Then** 既有已加载条目不被重复追加。

---

### User Story 2 - 全局视觉风格一致（Phase C）(Priority: P1)

用户在首页、播放页、订阅源页、设置页、队列面板等所有界面看到统一且协调的视觉语言——同一套色彩、圆角、间距、字号标准，同类部件（列表行/卡片/弹窗/空态）样式一致，不再出现各页面各自硬编码的观感差异。

**Why this priority**: 视觉统一提升整体品质感，是界面层面的地基；令牌层风险低、见效直观，组件规范在其之上进一步归一重复部件。

**Independent Test**: 逐页对照令牌与组件规范，确认所有颜色/圆角/间距/字号均来自统一来源，同类部件跨页面样式一致。

**Acceptance Scenarios**:

1. **Given** 任一页面，**When** 提取其色彩值，**Then** 全部来自令牌定义，无页面级散落色值。
2. **Given** 任一页面，**When** 提取其圆角/间距/字号值，**Then** 全部落在令牌档位表内，无档位外裸数字。
3. **Given** 同类部件（列表行/卡片/弹窗/空态）跨页面比较，**When** 检查其样式，**Then** 遵循同一组件规范，观感一致。
4. **Given** 深浅色两套外观，**When** 切换外观，**Then** 所有页面颜色正确跟随且无漏改硬编码。
5. **Given** 重构后运行，**When** 走查主要页面，**Then** 视觉观感与重构前一致或更协调（令牌替换数值不变，仅统一标准）。

---

### User Story 3 - 开发者维护时职责清晰（Phase D）(Priority: P2)

开发者（项目维护者）维护代码时，能快速定位「某类功能属于哪个模块、依赖谁、被谁依赖」，模块边界与依赖方向清晰，不再出现职责混杂的单文件上帝对象。

**Why this priority**: 提升可维护性，为后续 V2 迁移（Phase E）铺路；行为零变化，风险低。

**Independent Test**: 依据新边界文档，对任意服务/页面做「职责归属」抽查，均无跨边界依赖。

**Acceptance Scenarios**:

1. **Given** 服务层各文件，**When** 检查依赖方向，**Then** 遵循「服务 → 模型、页面 → 服务」的单向依赖，无反向/循环依赖。
2. **Given** 任一重构前存在的功能，**When** 回归走查，**Then** 行为与重构前完全一致（纯结构调整）。
3. **Given** 工程文档，**When** 查看模块边界说明，**Then** 每个模块的职责、允许依赖、禁止依赖均有明确描述。

---

### User Story 4 - 渐进迁移到新状态管理范式（Phase E，远期）(Priority: P3)

开发者按「模型层 → 独立组件 → 页面 → 全局状态」的顺序，把状态管理从 V1 渐进迁移到 V2。每个迁移单元独立完成、独立验证、可回滚，全程应用可用，不存在一次性大爆炸改造。

**Why this priority**: V2 是 HarmonyOS 官方新推荐范式，长期收益高；但风险最高、耗时最长，故列远期，本期仅规划路线图不实施。

**Independent Test**: 每个迁移单元完成后，该单元功能回归通过，且未迁移部分不受影响。

**Acceptance Scenarios**:

1. **Given** 模型层迁移单元，**When** 完成迁移，**Then** 纯数据类改为 V2 观测模型，不触碰任何 UI。
2. **Given** 任一已迁移页面，**When** 回归该页功能，**Then** 行为与迁移前一致。
3. **Given** 全局状态迁移（最后阶段），**When** 完成切换，**Then** 依赖它的所有页面已先行迁移，无观察断裂。
4. **Given** 迁移全程，**When** 任意时刻构建并运行，**Then** 应用可用（每块可独立交付）。

---

### Edge Cases

- API 26 为既定前提：应用不再支持 API<26 设备安装，需在产品说明/商店信息中同步最低版本要求。
- KI-9 修复时，若某链路请求失败走另一链路，翻页锚点必须跨链路保持有效，避免「降级后页界错位继续累积」。
- 视觉令牌替换时，纯替换不应改变既有观感；若个别页面依赖特定色值（如省流/无图模式），需保证令牌能表达该语义。
- 架构重构不得改动任何用户可见行为；涉及 `Constants`（唯一真相源）的迁移需保持键名稳定，防止破坏持久化数据。
- V2 迁移边界规则：单个页面内部 V1/V2 装饰器不可混用；V1 状态不得持有 `@ObservedV2` 实例；V1 的 `AppStorage` 与 V2 的 `AppStorageV2` 不互通——全局存储切换须在相关页面全部迁移后进行。

## Requirements

### Functional Requirements

**全局前提（Phase A）— API 26 基线化（前置落地项，非独立用户故事）**

- **FR-A-001**: 系统必须将工程兼容基线 `compatibleSdkVersion` 从 `6.1.1(24)` 提升至 `26.0.0`，与 `targetSdkVersion` 对齐。
- **FR-A-002**: 系统必须移除全部 `[API24-COMPAT]` 守卫标记（当前唯一处：`MediaSession.ets` 的 `setMediaCenterControlType`），保留防御性 try/catch 但不带兼容标记注释。
- **FR-A-003**: 系统必须将应用版本号提升为 0.3.0（versionCode 3000），标识本次重构里程碑。
- **FR-A-004**: 系统必须同步更新活跃文档：`AGENTS.md`、`PROJECT_NOTES.md` §四、`spec/ui-testing-playbook.md`，移除低版本兼容描述；历史 spec 轮次文档不得改动。
- **FR-A-005**: 系统基线化后，必须能在 API 26 设备上构建、安装、运行，播控中心五元组按钮可用。
- **FR-A-006**: 本次规划所有阶段均以 API 26 为基线，不引入任何 API<26 兼容设计或运行时守卫。

**Phase B — KI-9 页界统一**

- **FR-B-001**: 系统必须保证订阅源翻页时，APP 签名链与 Web 退避链使用一致的页大小或等效记账机制，链路切换/降级后不产生漏条或重复。
- **FR-B-002**: 系统必须保持翻页锚点（cursor/页码）跨链路有效。
- **FR-B-003**: 系统必须保证既有去重兜底（bvid 去重）继续生效，不因页界调整而失效。

**Phase C — 界面风格统一（设计令牌 + 组件规范）**

- **FR-C-001**: 系统必须统一定义色彩/圆角/间距/字号令牌：圆角收敛为有限档位（如 8/12/16/20），字号收敛为有限档位（如 10/11/13/14/16/22），间距收敛为有限档位（如 4/8/12/16/24），形成唯一可引用的标准集合。
- **FR-C-002**: 系统必须将页面/组件中散落的硬编码视觉值（裸数字圆角/字号/间距、残余散落色值）替换为令牌引用，保持浅色/深色外观语义正确。
- **FR-C-003**: 令牌替换必须不改变既有观感（替换数值不变、纯标准化），并覆盖省流/无图模式等特殊语义。
- **FR-C-004**: 系统必须建立组件规范：列表行/卡片/弹窗/空态等重复部件的样式归一（结构、令牌组合、状态样式），跨页面一致。
- **FR-C-005**: 组件规范落地后，同类部件跨页面观感一致，且不回归既有深浅色/主题色适配。

**Phase D — 架构边界重构（等级 1）**

- **FR-D-001**: 系统必须保持现有单例范式与 V1 状态管理范式，不引入范式切换。
- **FR-D-002**: 系统必须建立并记录模块边界：依赖方向单向（服务 → 模型；页面 → 服务），消除反向/循环依赖与职责混杂。
- **FR-D-003**: 系统必须保证本次重构零功能行为变化（纯结构调整），并以回归走查验证。

**Phase E — V2 渐进迁移路线图（远期，仅规划）**

- **FR-E-001**: 系统必须产出 V2 渐进迁移路线图，按「模型层 → 独立组件 → 页面 → 全局状态」划分迁移单元，每个单元独立可验证、可回滚。
- **FR-E-002**: 路线图必须明确迁移边界规则（单页内范式不混用、V1 不持有 V2 实例、全局存储最后切换），防止观察断裂。
- **FR-E-003**: 路线图必须标注风险最高、置于最后的单元（全局状态 + 播放器核心），以及每块迁移的验收方式。

### Key Entities

- **订阅源链路（UpSourceChain）**：APP 签名链与 Web 退避链，页大小（20 vs 30）与翻页锚点语义（Phase B 关注）。
- **设计令牌（DesignToken）**：色彩/圆角/间距/字号的标准化取值集合（Phase C 关注）。
- **模块边界契约（ModuleBoundary）**：服务/模型/页面的职责与依赖方向约定（Phase D 关注）。
- **迁移单元（MigrationUnit）**：V2 迁移的最小独立交付块，含边界与验收（Phase E 关注）。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 全局前提落地后，`[API24-COMPAT]` 标记检索为零命中；构建通过，API 26 设备安装运行正常。
- **SC-002**: 订阅翻页在链路降级/回切场景下，全量条目无漏无重（对照数据全量比对一致）。
- **SC-003**: 界面硬编码视觉值全局替换后，令牌覆盖率 ≥95%（残余为必须字面量的场景并明确登记）；圆角/间距/字号全部落在档位表内。
- **SC-004**: 组件规范落地后，列表行/卡片/弹窗/空态四类部件跨页面样式一致（对照走查零差异）。
- **SC-005**: 架构重构后回归走查通过率 100%，无用户可见行为变化。
- **SC-006**: V2 迁移路线图覆盖全部页面/服务/模型的迁移单元映射，每单元含独立验收标准；本期实施为零改动。

## Assumptions

- **本次只做规划**：交付 `spec/plan/tasks` 三份文档，不实施任何代码改动；各阶段实施在后续轮次按路线图推进。
- **API 26 为既定前提**：规划整体基于 API 26，不设任何 API<26 兼容设计/守卫；API 24/25 设备不再支持。
- 版本号随本次里程碑提升至 0.3.0/3000。
- `MediaSession.ets` 守卫移除采用「删标记、保留 try/catch」方式，保证控制类型设置失败不影响会话初始化。
- 构建配置（除 FR-A-001 的 compatibleSdkVersion 提升外）、依赖（oh-package/hvigor 已为 26）、签名体系、module.json5 无需改动。
- 历史 spec 轮次文档（各 `spec/*/plan.md`/`tasks.md`）属历史记录，不改动。
- 架构重构保持 V1 范式；V2 迁移仅列路线图，不实施。

## Open Questions

- **KI-9 实施方案选择**：Web 链页大小降为 20（改动小）与「翻页记账按链路分别校准」（改动大、更彻底）二选一——在 plan 阶段评估后定，需用户确认。
- **组件规范范围**：四类部件（列表行/卡片/弹窗/空态）的具体样式归一细节，在 plan 阶段产出规范草案后定。
- **架构边界重构裁剪**：具体哪些服务/文件需调整职责或位置，在 plan 阶段产出边界诊断后定，需用户确认裁剪幅度。
