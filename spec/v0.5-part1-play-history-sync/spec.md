# Feature Specification: 播放进度云端同步（v0.5）

**Created**: 2026-10-13  
**Status**: Draft  
**Input**: User description: "我的目的是同步进度，与 B 站做对接，可参考项目 PiliPlus"（前序铺垫：play-history-progress 轮已完成本地历史模型对齐 B 站 + HistoryMapper 映射边界预留）

## Overview

登录用户的播放进度与 B 站云端双向同步：本 app 播放中周期上报进度（心跳），B 站网页/APP 端可见听到哪了；起播时读取云端进度实现跨设备续听（其他设备看了一半的内容，本 app 接着听）。本轮**仅做进度同步**——不做云端历史列表拉取合并（历史面板维持现状，只显示本 app 产生的本地历史）、不做删除联动。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 播放中进度上报云端 (Priority: P1)

登录且同步开启的用户在本 app 播放任意内容，播放进度自动同步到 B 站云端：播放中周期上报（参照 PiliPlus 心跳节奏：进度每前进约 5s 上报一次），暂停/切歌时即时补报，网络失败静默放弃不阻塞播放。上报节奏挂接在现有进度节拍（`updateHistoryProgressForCurrent` 的 5s 节拍）之上，不新增独立计时器。

**Why this priority**: 「同步进度」的上行半边，无上报则云端无数据、下行续播无从谈起。

**Independent Test**: 登录后播放任意内容 ≥10s，在 B 站网页版「历史记录」中查看该视频，进度应更新为当前播放位置。

**Acceptance Scenarios**:

1. **Given** 已登录且开关开启，**When** 播放某内容并推进 ≥5s，**Then** B 站云端该内容进度更新（网页历史记录可见新进度）
2. **Given** 播放中网络断开，**When** 心跳上报失败，**Then** 播放不受任何影响，无错误弹窗，恢复后继续上报
3. **Given** 未登录或开关关闭，**When** 播放内容，**Then** 不发起任何上报请求，本地历史照常记录

---

### User Story 2 - 起播云端续播（跨设备续听） (Priority: P1)

用户在 B 站网页/APP 看了某视频到一半，在本 app 内通过搜索/订阅/收藏夹找到同一内容点开播放：起播时读取云端进度，从云端位置接着听。本地已有更新的进度时（刚在本 app 听过）不被云端旧数据回退。云端进度读取失败时回退纯本地续播逻辑（现状行为不变）。

**Why this priority**: 「同步进度」的下行半边，是跨设备续听的核心价值。

**Independent Test**: 在 B 站网页版观看某视频至中途，本 app 播放同一 bvid，起播位置应为云端进度附近（误差 ≤5s）。

**Acceptance Scenarios**:

1. **Given** 本地历史无某 bvid 记录（仅其他设备看过），**When** 本 app 播放该内容，**Then** 起播位置为云端进度（非从头）
2. **Given** 本地刚播放过该内容（本地进度更新），**When** 再次起播，**Then** 续播位置仍以较新一侧为准，不发生进度回退
3. **Given** 云端进度获取失败（网络异常），**When** 起播，**Then** 回退现有本地续播逻辑，播放正常

---

### User Story 3 - 完播状态同步 (Priority: P2)

本 app 听完某内容（自然播完或达完播阈值）时，向云端上报「已看完」语义（对齐 B 站 progress=-1）；云端已看完的内容在本 app 重播时从头播放（与本地 `-1 重播从头` 语义一致）。

**Why this priority**: 完播是进度的特殊值，不同步会导致其他设备显示「看了一半」的脏状态。

**Independent Test**: 本 app 完播某内容后，B 站网页历史记录中该视频显示为已看完；再次播放该内容，从头开始。

**Acceptance Scenarios**:

1. **Given** 播放至自然完播，**When** 完播事件触发，**Then** 云端该内容标记为已看完
2. **Given** 云端某内容已看完，**When** 本 app 起播该内容，**Then** 从头播放（不从尾部进度续播）

---

### User Story 4 - 同步开关 (Priority: P2)

设置页登录状态条目下方新增「历史同步」开关行，登录用户默认开启；关闭后上行上报与下行云端续播全部停用，行为回到现状纯本地逻辑。开关状态持久化（AppStore）；未登录时不显示该开关行（同步依赖登录态）。

**Why this priority**: 用户对「数据上传」的控制权（隐私退出通道），非核心闭环但属合规必要。

**Independent Test**: 关闭开关后播放内容，B 站云端进度无变化；重新打开后恢复同步。

**Acceptance Scenarios**:

1. **Given** 已登录，**When** 在设置页关闭「历史同步」，**Then** 播放期间无任何上报请求、起播不读云端进度
2. **Given** 开关关闭后杀进程重启，**When** 打开设置页，**Then** 开关保持关闭状态
3. **Given** 未登录，**When** 打开设置页，**Then** 登录状态条目下方不显示「历史同步」开关行；登录成功后出现且默认开启

---

### Edge Cases

- **离线播放**：本地进度照常记录；恢复联网后起播，本地新进度不被云端旧进度覆盖（判新以较新侧为准）
- **未登录**：同步整体静默禁用，不报错、不弹窗，本地历史/续播照常
- **快速切歌**：连续切换内容时心跳上报不串台（cid/bvid 与当前播放内容一致）
- **拖动进度条/快进**：上报进度反映最终位置，无需追报中间位置
- **睡眠定时暂停/后台播放**：心跳随播放状态启停，暂停即停报（补报一次后停）
- **登录失效（cookie 过期）**：上报/读取静默失败降级为纯本地，不反复弹登录提示
- **重播已听完内容**：本地 `-1→0` 重置后，上报进度随之归零重记（B 站语义：看完重看从头记）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 已登录且开关开启时，系统 MUST 在播放中周期上报当前进度到 B 站云端（节奏参照 PiliPlus：进度每前进 ≥5s 上报一次；暂停/切歌/完播等状态变化时即时补报）。
- **FR-002**: 完播时系统 MUST 向云端上报已看完语义（progress=-1，对齐 B 站「-1=看完」）。
- **FR-003**: 起播时系统 MUST 尝试获取该内容的云端播放进度；本地无该条历史时 MUST 从云端进度续播。
- **FR-004**: 本地进度与云端进度不一致时，系统 MUST 以较新一侧为准，MUST NOT 发生可感知的进度回退（已听过的部分不重播、未听部分不跳过）。判新的具体依据（云端响应是否携带时间戳）在设计阶段确定。
- **FR-005**: 设置页 MUST 在登录状态条目下方提供「历史同步」开关行（登录用户默认开启），开关状态 MUST 持久化；关闭后上行/下行同步全部停用；未登录时 MUST 隐藏该开关行。
- **FR-006**: 未登录或登录失效时，同步功能 MUST 静默禁用（无错误弹窗、无循环重试），本地历史与续播行为维持现状。
- **FR-007**: 上报与云端读取 MUST 为尽力而为（best-effort）：失败静默记日志，不阻塞播放、不弹错误。
- **FR-008**: 云端进度获取失败时，系统 MUST 回退现有纯本地续播逻辑。
- **FR-009**: 本轮 MUST NOT 拉取/合并云端历史列表（`/x/v2/history` 列表接口不在范围），历史面板 UI 与语义零改动。
- **FR-010**: 本轮 MUST NOT 做删除联动（本地删除/清空不删云端，反之亦然）。
- **FR-011**: 上报请求 MUST 复用现有登录态（BiliSession cookie）与既有 HTTP 基础设施（buildHeaders/WbiSigner），不引入新登录方式。

### Key Entities *(include if feature involves data)*

- **播放历史条目（PlayHistoryItem，无新增）**: 复用现有模型（progress/duration 秒、viewAt 秒级时间戳、-1=看完），本轮零结构改动。
- **云端进度（起播输入）**: 起播时从取流响应读取的该内容云端播放进度（来源与字段名在设计阶段验证确定），仅作为续播决策输入，不落盘为独立状态。
- **同步开关（SyncEnabled，新增持久化偏好）**: 「历史同步」开关状态，KEY_* 持久化键（Constants 登记）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 登录+开关开启状态下播放任意内容 ≥10s 后，B 站网页版历史记录中该内容进度与实际播放位置误差 ≤5s。
- **SC-002**: 在 B 站网页/APP 观看某视频至中途，本 app 播放同一内容，起播位置与云端进度误差 ≤5s。
- **SC-003**: 本 app 完播的内容，B 站云端显示已看完；再次播放从头开始。
- **SC-004**: 关闭开关后播放任意内容，B 站云端进度零变化；本 app 起播行为与开关关闭前纯本地逻辑一致。
- **SC-005**: 同步全程（上报失败、云端读取失败、未登录）对播放主流程零可感知影响（不中断、不卡顿、无弹窗）。

## Assumptions

- 现有扫码登录态（SESSDATA/bili_jct cookie）可直接用于上报与云端读取，无需新增鉴权。
- 心跳上报端点与参数参照 PiliPlus（web heartbeat 系），具体端点/参数/签名要求在设计阶段以实测为准。
- 云端进度预期由取流响应携带（参照 PiliPlus `last_play_time`）；本项目当前取流端点（`/x/player/playurl`）是否返回该字段待设计阶段验证，若不返回则调整取流端点/参数或改用其他单条查询路径——设计决策，不扩需求范围。
- 历史面板、队列、睡眠定时等既有功能语义零改动；`HistoryMapper`/`PlayHistoryItem` 既有对齐成果直接复用。
- 心跳为小体积请求（音频场景无视频流量），不做流量敏感设计。
- 参照项目：`../bili/PiliPlus`（心跳节奏/端点/开关交互）、`../bili/biliRelay`（API 行为佐证）。

## Open Questions

- 取流端点 `/x/player/playurl` 响应是否携带云端进度字段（`last_play_time`）？不携带时切换 `player/wbi/v2`（需 WBI 签名，WbiSigner 已具备）还是另寻单条历史查询？——Phase 2 实测验证后定。
- 本地与云端进度判新的具体规则：云端响应若不含时间戳，如何界定「本地较新」（离线播放/刚完播场景）？——Phase 2 结合响应实测定。
